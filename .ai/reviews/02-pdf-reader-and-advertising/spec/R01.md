## 1. Summary

The spec already describes what the owner wants: cover alone, then two-page spreads (2–3, 4–5 …) on wide screens, one page on narrow screens, previous/next controls, no flipbook animation, an HTML banner above the reader. Its boundaries (ad independent of the PDF, honest failure states, no CMS calls on page turns) are sound.

What needs work:

1. **The layout does not fit the screen.** With "fit-to-width" as the default, two A4 pages on a 1280–1440 px desktop are about 900 px tall — more than the whole viewport before the header, banner and controls are counted. The bottom arrows end up below the fold, so every page turn requires scrolling. (F01)
2. **The page-step rule must be confirmed with the owner** — "left page becomes what was on the right" can be read as a one-page slide (2–3 → 3–4) rather than a magazine spread turn (2–3 → 4–5). (F02)
3. **Page turns will feel slow without render-ahead.** With no animation, the next spread must appear instantly; the spec forbids preparing it unless measurements justify it. (F03)
4. **Fixtures, delivery and real PDFs** conflict with current rules (no links to the old voc.sk) or are unknown. (F05–F07)

## 2. Findings

### R01-F01 — Blocker — Default "fit-to-width" makes the spread taller than the viewport; bottom controls fall below the fold

- **Location:** §Page Structure (lines 71–80: banner, surface, "Bottom controls"; "Allow page/viewport scrolling when needed"), §Controls and Zoom (line 110: "Initial zoom is fit-to-width").
- **Problem:** A4 is 1 : 1.414. In a 1300 px container each page of a spread is ~650 px wide and ~920 px tall. A 1440×900 laptop has ~824 px below the 76 px header — before the banner (up to 250 px) and the control bar. At "fit-to-width" the reader cannot show a whole spread, and the "Predchádzajúca / Nasledujúca" buttons at the bottom are off-screen.
- **Impact:** The core interaction (look at both pages, click the arrow) requires scrolling up and down on every turn — the opposite of "like an opened magazine".
- **Recommendation:**
  - Default zoom = **fit the whole spread to the available height and width** ("Celá dvojstrana"), so banner + spread + controls fit one desktop viewport. Keep fit-to-width and zoom-in as explicit options.
  - Make the reader area a viewport-height stage: `100svh − header − banner − control bar`, measured, not guessed.
  - Put the navigation **where the eye is**: large previous/next buttons at the left and right edges of the spread (vertically centred), plus the bottom bar with page indicator, "Prejsť na stranu" and zoom. The owner's "bottom left/right" request is satisfied by the bar; edge arrows make turning effortless. Confirm placement with the owner.
  - Choose a **short banner format** so it does not crush the spread height (see F09).

### R01-F02 — High — Page-step rule needs explicit owner confirmation

- **Location:** §Page and Spread Rules (lines 84–99).
- **Problem:** The owner described the turn as "the right page changes to a new one and the left one changes to what was on the right". That is either:
  - **(a) Magazine spread turn** (what the spec specifies): 1 → 2–3 → 4–5 → 6–7. Both pages change; it matches a printed magazine and keeps designed double-page spreads (ads, photos across the fold) together.
  - **(b) One-page slide**: 1–2 → 2–3 → 3–4. The right page moves to the left. Double-page spreads are shown split across two views; it is unlike a magazine.
- **Impact:** Implementing the wrong one is visible immediately and invalidates the pairing rules and their tests.
- **Recommendation:** Confirm (a) with the owner using a concrete example ("after pages 2–3 you see 4–5"), then record the confirmed behaviour verbatim in the spec. Keep the existing rules for odd/even endings, page 1 alone and focused-page preservation — they are correct for (a).

### R01-F03 — High — No render-ahead: without animation, every turn shows a blank or loading spread

- **Location:** §Rendering and Memory (line 188: "Start with only the current one/two page canvases mounted … optional bounded next-spread preparation can be added only when measurements justify it").
- **Problem:** Rendering a magazine page at desktop density can take a few hundred milliseconds or more (large images, range requests for not-yet-downloaded data). With no page-turn animation to hide it, the user clicks "next" and sees an empty or loading spread.
- **Impact:** The reader feels slow and cheap even if everything is technically correct.
- **Recommendation:** Make **bounded render-ahead the default**: after the current spread settles, prepare the next spread (and keep the previous one) off-screen — at most 6 page canvases in memory on desktop, 3 on mobile; drop anything further away. Swap in the prepared canvases on click. Measure on a mid-range phone and lower the limit if memory requires it.

### R01-F04 — Medium — Mobile behaviour: single page is right, but navigation and legibility are under-specified

- **Location:** §Page and Spread Rules (line 97: spread at ≥ 1024 px), §Controls (line 115: "No custom swipe/pinch engine").
- **Problem:** On phones one A4 page at full width is readable only for large type; body text in a technical magazine is small. Phone users expect to swipe to the next page; tiny bottom buttons are the only route in the spec. Tablets in portrait (768–1023 px) get a single page; in landscape a spread at ~500 px per page may be illegible.
- **Recommendation:** Add a simple horizontal **swipe** (pointer events with a distance threshold, ignored while zoomed) — small cost, large usability gain. Define tablet behaviour explicitly (e.g. spread only when each page would be ≥ 480 px wide, otherwise single page). Keep a "Zväčšiť" control that re-renders sharper and lets the user pan.

### R01-F05 — High — Fixtures point PDFs at the old voc.sk, which the project no longer allows

- **Location:** `data/mock/editions.ts:48,75` (`PdfAsset.url` → `https://voc.sk/wp-content/uploads/…`), §Data Flow and Fixtures (lines 141–151).
- **Problem:** The owner has banned links to the legacy site. Cross-origin loading by PDF.js would also need CORS headers that the old WordPress server is unlikely to send, and the site is being retired.
- **Recommendation:** State in the spec that reader fixtures are local files (`public/pdfs/…`; small QA files committed, large representative files outside git), and that production PDFs are Sanity file assets. Remove the voc.sk URLs from fixtures when unit 1 starts.

### R01-F06 — High — Real PDFs and the delivery host are unknown, but decide the whole performance plan

- **Location:** §File Delivery (lines 194–202), §Remaining Launch Inputs (lines 252–253), `domain/delivery-and-costs.md`.
- **Problem:** Print exports of a magazine are often tens of MB (sometimes 100 MB+), not linearized, with high-resolution images. Range loading helps only with linearized files on a host that serves byte ranges with CORS. No owner workflow, size limit or Studio validation is specified.
- **Recommendation:** Obtain two real issues now (typical and largest). Define a "reading PDF" rule (web/screen export preset, linearized, single pages not imposed, maximum size enforced in the Sanity schema once measured). Verify Sanity's file CDN for `206 Partial Content`, `Accept-Ranges` and CORS with an uploaded test file **before** freezing the PDF.js options.

### R01-F07 — High — Public PDF URLs bypass the banner and the site (including via search engines)

- **Location:** §Excluded (line 39), `domain/advertising.md` (lines 38–40).
- **Problem:** Search engines index PDFs; visitors can land on the raw file without banner or navigation. The spec notes the URL is public but records no decision.
- **Recommendation:** Record an explicit owner decision: accept it, or mitigate (e.g. `X-Robots-Tag: noindex` — requires controlling response headers, which may need a proxy and its bandwidth cost). State plainly that a web reader cannot make a public PDF private.

### R01-F08 — Medium — Entry points, canonical URL and indexing of the reader route

- **Location:** §Routes and Entry Points (lines 54–67); feature 01 edition page with the "Chcete toto číslo?" panel and the "Čítanie online pripravujeme" status.
- **Problem:** Two URLs per edition (`/vydania/4-2026` detail, `/citat/4-2026` reader) without defined linking, canonical or indexing rules; the reader's content is canvas (thin HTML).
- **Recommendation:** Edition detail stays canonical and indexable; the reader route is `noindex` (or canonicalised to detail). Primary entry: a prominent **"Čítať online"** button in the edition action panel when a PDF exists (replacing "Čítanie online pripravujeme"). Decide whether gallery cards for readable editions show a small "Čítať" affordance.

### R01-F09 — Medium — Ad slot geometry undecided; the default must be short

- **Location:** §Page Structure (line 82), §Remaining Launch Inputs (line 252).
- **Problem:** Stable geometry is required but no size is chosen. Because of F01 the banner height directly reduces how large the spread can be.
- **Recommendation:** Start with a **leaderboard-style strip**: desktop 970×90 (or 728×90), mobile 320×100, artwork `object-fit: contain` on a neutral slot, labelled "Inzercia". Validate minimum width/aspect in Studio. The local fallback banner in `public/` uses exactly the same geometry. Revisit only if the owner sells a larger format.

### R01-F10 — Medium — Advertising model is heavier than the requirement

- **Location:** `domain/advertising.md` (placement + ordered candidates + selected creative + fallback), §Advertising (lines 153–165).
- **Problem:** The owner requirement is "one banner per magazine, added manually in Sanity, placeholder fallback". The spec prepares candidate lists and selection validation for an unapproved rotation.
- **Recommendation:** v1: a `readerBanner` object on each magazine (enabled, desktop image, optional mobile image, alt text, optional link) plus one site-wide house banner, resolved by a pure `resolveReaderAd()` function. Keep that function boundary so rotation can be added later; drop candidate lists until rotation is specified.

### R01-F11 — Medium — PDF.js security and asset configuration missing

- **Location:** §Rendering Architecture (lines 117–139).
- **Problem:** pdf.js had a high-severity issue (CVE-2024-4367, fixed in 4.2.67) allowing script execution from a crafted font when `isEvalSupported` is on. Editors (or advertisers supplying PDFs) are a plausible vector.
- **Recommendation:** Require a pdf.js version at or above the fix (React-PDF bundles its own `pdfjs-dist`; check the resolved version), `isEvalSupported: false`, the worker served from our origin, and `cMapUrl` / `standardFontDataUrl` pointing to local static files so Slovak diacritics in non-embedded fonts render.

### R01-F12 — Medium — Engine choice should be confirmed in a short spike, not assumed

- **Location:** §Status (line 7), Unit 2 (line 242).
- **Problem:** React-PDF is a reasonable fit for a paged viewer (two `<Page>` components per view). Alternatives were not recorded: `pdfjs-dist` directly (more control over canvas reuse for render-ahead, F03), PDF.js's own viewer with spread mode, or pre-rendered page images (excluded at lines 36 and 43 — the fastest option on phones, with no text selection).
- **Recommendation:** Keep React-PDF as the working choice but make unit 2 a **spike with real PDFs** that also checks render-ahead (F03), Next.js 16 / Turbopack worker loading and the pdf.js version (F11). Record the decision and measured limits in `architecture-context.md`.

### R01-F13 — Medium — Spec status and unit order

- **Location:** §Status (line 5: "Specification ready for implementation"), §Implementation Units (lines 239–248), `ai-workflow-rules.md` (Handling Missing Requirements).
- **Problem:** F01/F02/F06/F09 are unresolved inputs, yet the spec is marked ready and unit 1 starts with contracts and fixtures.
- **Recommendation:** Status "In review". Order: **Unit 0 spike** (real PDFs, host range/CORS, render-ahead, layout fit) → owner confirmation of F02 and banner size → contracts/fixtures → reader shell and spread layout → banner → entry points → Sanity. Record open questions in `progress-tracker.md`.

### R01-F14 — Low — Spec not reconciled with feature 01 outcomes

- **Location:** whole document.
- **Problem:** Edition highlights were removed; the edition page now has a dedicated action panel; legacy voc.sk links are banned; an `/inzercia` page exists.
- **Recommendation:** House banner action → `/inzercia` (or e-mail); entry point from the edition action panel; local fixtures; reader pages must not link to legacy URLs.

### R01-F15 — Low — Download button decision deferred but affects the layout and the ad

- **Location:** §Excluded (line 39), §Remaining Launch Inputs (line 255).
- **Recommendation:** Ask the owner now. If "no", record the reason (downloaded files carry no banner) so it is not re-opened later.

## 3. Edge cases for the acceptance table (additions)

| # | Situation | Expected |
| --- | --- | --- |
| 1 | 1440×900 and 1366×768 desktop | Banner, whole spread and controls visible without page scrolling at default zoom |
| 2 | Click "next" repeatedly and fast | Latest target wins; prepared spreads are reused; no stale spread shown as the new one |
| 3 | PDF contains a page wider than tall (double page exported as one sheet) | Shown alone, fitted; pairing continues correctly after it — or flagged as unsuitable at upload |
| 4 | Mixed page sizes (inserts, covers) | Each page fitted without cropping; spread aligned on a shared baseline |
| 5 | Swipe on phone while zoomed | Pans the page, does not turn it |
| 6 | Tablet portrait → landscape at page 13 | Single 13 → spread 12–13; back to portrait shows 13 |
| 7 | Network drops after a few spreads | Already rendered spreads keep working; next one shows inline error + retry |
| 8 | Password-protected / corrupt PDF | Unsupported state; banner, edition info and back link stay |
| 9 | Banner image fails / placement disabled | House banner in identical geometry; spread size unchanged |
| 10 | Keyboard: ←/→ with reader focused; typing in "Prejsť na stranu" | Arrows turn pages only when focus is not in the input |

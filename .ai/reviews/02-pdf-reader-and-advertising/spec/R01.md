## 1. Summary

The spec is careful about boundaries, ad independence, caching and honest failure states, and most of that should survive. Its core interaction model does not:

1. The owner now wants a **scrolling reader** (open the magazine, scroll through pages, no page-turn animation, banner on top). The spec describes a **paged spread viewer** (prev/next, spread pairing, page input, keyboard paging, one/two mounted canvases, scroll reset on navigation). Roughly a third of the document — page/spread rules, controls, memory model, acceptance table, unit 3 — is built on paging.
2. The **engine decision (React-PDF)** was made for the paged model. React-PDF renders `<Page>` components but has no virtualization or scroll-mode viewer; PDF.js's own viewer layer (`pdfjs-dist/web/pdf_viewer`) does. The decision must be re-evaluated against scrolling.
3. **Real source PDFs, delivery host and banner geometry are all unknown**, yet the spec is marked "ready for implementation". A short technical spike with two real issues should precede any contract work.
4. Since feature 01 shipped, several facts the spec relies on changed (owner forbids links to the old voc.sk; fixtures still point PDFs at voc.sk; edition page now has a dedicated "Čítanie online pripravujeme" slot; edition highlights were removed). The spec has not been reconciled with them.

## 2. Findings

### R01-F01 — Blocker — Interaction model contradicts the owner requirement (paging vs. scrolling)

- **Location:** §Status (line 7), §Scope/Included (lines 24–26), §Page and Spread Rules (lines 84–99), §Controls and Zoom (lines 101–115), §Acceptance (lines 218–233), Unit 3 (line 243).
- **Problem:** The spec defines discrete views (cover alone, then 2–3, 4–5 …), prev/next buttons, a focused-page state machine, keyboard paging and "reset the page viewport's scroll to its top" on navigation. The owner requirement is: open the magazine and **scroll**; no page animation; banner on top.
- **Impact:** Implementing the spec as written produces the wrong product. Pure page-pairing logic, unit tests and acceptance rows (7-page / 6-page spread sequences, mode switching at page 13) become dead work.
- **Recommendation:** Replace §Page and Spread Rules and §Controls with a continuous vertical scroll model:
  - All pages stacked in one column, each page box reserved at its correct aspect ratio before rendering (no layout jump).
  - Page indicator derived from the page that occupies most of the viewport (`Strana 12 z 80`), plus "Prejsť na stranu" that scrolls to the page.
  - Zoom (fit-to-width default, bounded steps) re-renders visible pages and keeps the reading position anchored to the current page.
  - Optional later: two-column "spread scroll" on wide screens — decide explicitly, do not keep both models in v1.
  - Delete the pairing rules and their tests; keep the "one-based physical page numbers" rule.

### R01-F02 — Blocker — Memory/rendering model is incompatible with continuous scroll

- **Location:** §Rendering and Memory (lines 186–192), §Acceptance row "Long issue repeatedly navigated/closed".
- **Problem:** "Start with only the current one/two page canvases mounted. No off-screen canvas buffer … never render the entire issue." In scroll mode several pages are partially visible at once, and pages just outside the viewport must be ready or the user scrolls into blank boxes.
- **Impact:** Either blank pages during scrolling or an implementation that silently violates the spec. Without an explicit render window, the naive scroll implementation renders all 60–100 pages and exhausts mobile memory (iOS Safari is the usual failure point).
- **Recommendation:** Specify a **virtualized render window**: render pages intersecting the viewport plus a bounded buffer (e.g. 1–2 pages above/below); cancel render tasks for pages that leave the window; release canvases beyond it (reset canvas width/height so memory is actually freed); cap simultaneous canvases; keep lightweight placeholders with correct size for all other pages. Add acceptance rows for a fast fling from page 1 to page 60 (intermediate renders cancelled, no blank final view) and bounded canvas count after scrolling the whole issue.

### R01-F03 — High — Engine choice (React-PDF) not evaluated against alternatives for the new model

- **Location:** §Status (line 7), §Rendering Architecture (lines 117–139), Unit 2.
- **Problem:** React-PDF is a thin React wrapper around PDF.js's `Document`/`Page`. For scrolling we would have to build virtualization, render queueing, zoom anchoring and text/annotation layer management ourselves. PDF.js ships a production viewer layer (`pdfjs-dist/web/pdf_viewer`: `PDFViewer`, `EventBus`, `PDFLinkService`) that already implements vertical scroll mode, lazy visible-page rendering with a render queue, zoom with re-render, text layer and link annotations — it is what Firefox's built-in viewer uses.
- **Impact:** Picking React-PDF for a scroll reader likely means re-implementing the hard parts of PDF.js's viewer, with more bugs and more time.
- **Recommendation:** Re-decide the engine through a spike (see §4). Options to compare, with the trade-offs recorded in the spec:
  1. **PDF.js viewer component** (`pdfjs-dist` + `pdf_viewer`) embedded in a client-only container below our HTML banner — recommended default.
  2. **React-PDF** with our own virtualization — more React-idiomatic, more custom code.
  3. **Pre-rendered page images** (WebP per page, generated once at upload) displayed as a lazy-loaded `<img>` list — simplest and fastest on mobile, no PDF.js, but no text selection/links and needs a conversion step (currently excluded at lines 36 and 43; reopen deliberately if the spike shows PDF.js struggling with real issues).
  4. **Hosted/embedded viewers** (native browser iframe, Adobe PDF Embed API in-line mode, Issuu/FlippingBook-type services) — fastest to ship but poor mobile support (native) or third-party scripts, branding, tracking and GDPR implications. Record why they are rejected.

### R01-F04 — High — Real source PDFs are unknown; the plan assumes "web-optimized reading PDFs" with no workflow that produces them

- **Location:** §File Delivery (lines 194–202), §Remaining Launch Inputs (lines 252–253), `domain/delivery-and-costs.md`.
- **Problem:** Magazine PDFs exported for print are commonly tens of MB (sometimes 100 MB+), not linearized ("Fast Web View"), with high-resolution CMYK images. Range-loading only helps if files are linearized and the host serves byte ranges. The spec says "serve a web-optimized reading PDF where supplied" but defines no owner workflow, no size limit and no validation in Studio.
- **Impact:** The first real upload can make the reader unusable on mobile (long time-to-first-page, memory crashes) and costly in bandwidth — exactly where the free-tier cost goal is at risk.
- **Recommendation:** Add an owner-facing "reading PDF" rule set: export preset (screen/web quality, linearized), a hard max size enforced in the Sanity schema (to be measured, not guessed), single-page (not imposed) pages, and a Studio help text. Obtain 2 real issues now (one large, one small) for the spike; measure size, page count, time to first page and memory on a mid-range phone before freezing the rendering approach.

### R01-F05 — High — Fixture and delivery assumptions conflict with the new "no old voc.sk" rule

- **Location:** `data/mock/editions.ts:48,75` (`PdfAsset.url` → `https://voc.sk/wp-content/uploads/…`), §Data Flow and Fixtures (lines 141–151), §File Delivery.
- **Problem:** The owner now forbids linking to the legacy voc.sk. The only "available" PDFs in fixtures are served from it. Cross-origin fetches from PDF.js also need CORS on that host, which the old WordPress server is unlikely to send, and that host will be retired.
- **Impact:** The reader cannot be demonstrated with current fixtures; tests depend on an external site the project is replacing.
- **Recommendation:** Spec must state that reader fixtures are **local files** (`public/pdfs/…`, small QA files committed; large representative files kept out of git or in LFS), and that production PDFs are Sanity file assets. Add "verify CORS + `Accept-Ranges`/206 responses on the Sanity file CDN" as a spike item, not a launch item.

### R01-F06 — High — Banner placement loses its value in a scrolling reader

- **Location:** §Page Structure (line 78: "normal non-sticky block"), `domain/advertising.md` §Placement Limits.
- **Problem:** The spec fixes a non-sticky banner above the reader. With a paged viewer the banner stays near the content; with a long scroll it is visible only during the first seconds of reading.
- **Impact:** The paid placement — the commercial reason for the feature — is barely seen. Advertisers sold "on every edition" get one glance.
- **Recommendation:** Decide the layout explicitly before implementation. Options:
  - **(a) Reading-room layout:** page header + banner + reader pane whose height fills the remaining viewport and scrolls internally; the banner stays visible the whole time. Clean on desktop; on mobile needs care (nested scrolling, address-bar resize).
  - **(b) Page scroll + compact sticky ad strip** (thin version of the creative pinned under the header while reading).
  - **(c) Banner on top + repeated in-flow banner every N pages** (between pages, outside the PDF).
  Recommended: (a) on desktop, (b) or (c) on mobile; whichever is chosen, keep the ad as separate HTML and keep a reserved slot geometry.

### R01-F07 — High — Raw PDF URLs bypass the banner, the site and analytics (including via search engines)

- **Location:** §Excluded (line 39), `domain/advertising.md` (lines 38–40).
- **Problem:** The spec acknowledges public PDF URLs but stops there. Search engines index PDFs; visitors can land directly on the raw file from Google, without banner or navigation. PDF.js also exposes the URL in network requests.
- **Impact:** Paid ad and site traffic leak; the owner may believe the ad is "on every view" when it is not.
- **Recommendation:** Record an explicit decision: accept public URLs, or mitigate (e.g. `X-Robots-Tag: noindex` — requires controlling response headers, which Sanity's CDN may not allow, implying a proxy and its bandwidth cost). Tell the owner plainly that a web reader cannot make a public PDF private.

### R01-F08 — Medium — Reader route vs. edition detail page: unclear user flow, SEO and canonical handling

- **Location:** §Routes and Entry Points (lines 54–67); feature 01 edition page (`/[magazine]/vydania/[edition]`) with the "Chcete toto číslo?" action panel and the "Čítanie online pripravujeme" status.
- **Problem:** Two pages per edition (`/vydania/4-2026` detail and `/citat/4-2026` reader) without defined linking rules, canonical URLs or indexing policy. The reader page's content is canvas-rendered (thin HTML).
- **Impact:** Duplicate/thin pages in search; inconsistent entry points (cards, edition page, homepage rail).
- **Recommendation:** Define: the edition detail page stays canonical and indexable; the reader route is `noindex` (or canonicalised to detail); the primary entry point is a "Čítať online" button in the edition action panel when a PDF exists (replacing "Čítanie online pripravujeme"); covers keep linking to the detail page. Consider whether the reader should be the edition page itself (one URL) — decide, don't leave implicit.

### R01-F09 — Medium — Advertising model is heavier than the requirement

- **Location:** `domain/advertising.md` (placement + ordered candidates + selected creative + fallback), §Advertising (lines 153–165).
- **Problem:** The owner requirement is "one banner per magazine, added manually in Sanity, with a placeholder fallback". The spec prepares placement documents, candidate lists and selection validation for a rotation that is explicitly not approved.
- **Impact:** More schema, validation and editor complexity in Studio for no current benefit; more places for misconfiguration (selected creative not in candidate list, etc.).
- **Recommendation:** v1: a `readerBanner` object on each magazine (enabled, desktop image, optional mobile image, alt text, optional link) plus one site-wide house banner, resolved by a pure `resolveReaderAd()` function. Keep the function boundary so rotation can be added later; drop candidate lists until rotation is specified.

### R01-F10 — Medium — Ad slot geometry is "undecided" but required to be stable

- **Location:** §Page Structure (line 82), §Remaining Launch Inputs (line 252).
- **Problem:** Stable geometry is required but no dimensions exist, so the slot, fallback artwork and Studio validation cannot be built consistently.
- **Recommendation:** Pick working defaults now and let the owner override: e.g. desktop 970×250 (aspect 97:25) and mobile 320×100 (16:5), artwork `object-fit: contain` on a neutral slot background, the image validated in Studio for minimum width and aspect tolerance. The fallback house banner (`public/…`) uses the same geometry.

### R01-F11 — Medium — Security hardening for PDF.js is missing

- **Location:** §Rendering Architecture.
- **Problem:** PDF.js had a high-severity issue (CVE-2024-4367, fixed in pdf.js 4.2.67) allowing script execution from a crafted font when `isEvalSupported` is enabled. PDFs come from an editor account; a compromised account or an advertiser-supplied PDF is a plausible vector. The worker also needs a CSP allowance.
- **Recommendation:** Require a pdf.js version at or above the fixed release, `isEvalSupported: false`, the worker served from our own origin (no third-party CDN), and document the CSP needs (`worker-src`) if a CSP is added. Configure `cMapUrl`/`standardFontDataUrl` from local static files so Slovak diacritics in non-embedded fonts render.

### R01-F12 — Medium — Scroll-specific states and edge cases are not specified

- **Location:** §States and Recovery (lines 167–182), §Acceptance.
- **Problem:** The state table covers document-level failures but not scroll-reader situations.
- **Recommendation:** Add (at minimum): deep link to a page (`#strana-12`) and restoring position on back navigation; mixed page sizes within one PDF (inserts, covers); a page that fails to render mid-document (placeholder with per-page retry, document stays usable); fast fling across many pages; orientation change keeping the current page anchored; text layer for many pages (DOM size); `Ctrl/⌘ +` browser zoom vs reader zoom; very small PDFs (1 page) and very large (150+ pages); encrypted/password PDFs; range-request failure mid-scroll (network drop after first pages loaded).

### R01-F13 — Medium — Zoom and touch behaviour are underspecified for scroll mode

- **Location:** §Controls and Zoom (lines 110–115).
- **Problem:** "No custom pinch engine" plus "preserve browser zoom" means mobile pinch-zoom scales low-resolution canvases (blurry text), and fit-to-width on a phone makes magazine body text small. Reader zoom buttons alone are awkward on touch.
- **Recommendation:** Decide the mobile reading strategy in the spike: e.g. fit-to-width with a single "Zväčšiť" toggle that re-renders at a higher scale and allows horizontal pan, versus pinch support from the viewer engine. Measure legibility of real body text at 360–390 px widths.

### R01-F14 — Medium — Workflow: spec marked "ready" while strategic inputs are open; units in wrong order

- **Location:** §Status (line 5: "Specification ready for implementation"), §Implementation Units (lines 239–248), `ai-workflow-rules.md` (Handling Missing Requirements).
- **Problem:** Engine choice, real PDFs, host behaviour, banner geometry and reader layout are unresolved; the workflow rules say ambiguous requirements are resolved in context before implementing. Unit 1 builds contracts and pure navigation rules before the engine is proven.
- **Recommendation:** Change status to "In review — awaiting spike". Reorder: **Unit 0: technical spike** (engine comparison on real PDFs, host CORS/range check, mobile memory) → decision recorded in architecture context → contracts/fixtures → reader shell → banner → entry points → Sanity. Record open questions in `progress-tracker.md`.

### R01-F15 — Low — Spec not reconciled with feature 01 outcomes

- **Location:** whole document; `content-model.md`, `ui-context.md`.
- **Problem:** Edition highlights were removed; the edition page now has a dedicated action panel; the owner banned links to old voc.sk; an `/inzercia` page now exists (house banner can link there instead of a mailto); external reference link to iFlip (line 17) remains as inspiration only.
- **Recommendation:** Update §Advertising (house banner → `/inzercia` or e-mail), §Routes (entry from the edition action panel), §Data Flow (local fixtures), and note that reader pages must not link to legacy URLs either.

### R01-F16 — Low — Download button decision is deferred but affects the layout

- **Location:** §Excluded (line 39), §Remaining Launch Inputs (line 255).
- **Problem:** Readers commonly expect "Stiahnuť PDF"; adding it later changes the toolbar and weakens the ad (downloaded files have no banner).
- **Recommendation:** Ask the owner now; if "no", state the reason in the spec (ad visibility) so it is not re-litigated.

## 3. Edge cases checklist (for the rewritten spec's acceptance table)

| # | Situation | Expected |
| --- | --- | --- |
| 1 | Open reader on a 4G phone with a 40 MB issue | First page visible quickly (target set after spike); later pages stream on scroll |
| 2 | Fling from page 1 to page 60 | Intermediate renders cancelled; landing pages render; no blank screen |
| 3 | Scroll whole issue top→bottom | Canvas count stays bounded; no memory crash on iOS Safari |

## 4. Recommended next step: a time-boxed spike (Unit 0)

1. Get two real issues from the owner (a typical one and the largest), plus one print-imposed export if it exists.
2. Build two throwaway prototypes on the same page shell with a placeholder banner:
   - PDF.js viewer component (`pdfjs-dist` + `pdf_viewer`) in vertical scroll mode;
   - React-PDF with simple IntersectionObserver virtualization.
3. Measure on desktop Chrome/Safari and one mid-range Android + one iPhone: bytes before first page, time to first page, smooth scrolling, memory after scrolling the full issue, text sharpness at fit-to-width, bundle size.
4. Check Sanity file CDN behaviour for byte ranges and CORS with an uploaded test PDF.
5. Record the decision and the measured limits in `architecture-context.md`, then rewrite §Page/Controls/Rendering/Acceptance/Units of this spec.

If PDF.js is too slow or memory-hungry on real files, reopen the excluded **pre-rendered page images** option (F03-3) with a cost estimate.
